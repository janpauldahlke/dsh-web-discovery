## 0. The real product (re-framed)

The core problem is in **missions**, not discovery:

> On `mission_start`, either the user pastes the URLs or the model "remembers" them. That leads to **bad URLs and lots of 404s**.

So the value of discovery is mostly **"real URLs instead of hallucinated ones"**. Ranking and categorizing come second. Any real SERP URL already beats a remembered one. That changes the priorities:

1. **Get it live and make the skill strict** (no invented URLs while discovery is on). That's the biggest win, and it costs almost nothing.
2. Cheap triage in the search receipt.
3. Optional categorizer.
4. Extra engines.

---

## 1. Constraint verdict

**Keep the "same sequential turn loop" as hard law for v0 and v1.**
`mission_fetch` already acts as the quality gate (`page_quality`). A subagent would add a second token stream on a box with no headroom (27B at 15 tok/s) and would only fix a problem we haven't measured.

## 2. Budget (concrete, sized to qwen 27B Q4 · 128k ctx · ~15 tok/s · compaction at 60–80%)

| Budget | Value | Why |
| --- | --- | --- |
| Discovery tool calls before the first `mission_fetch` | **≤ 2** (1 search + 1 optional reformulate) | Each turn costs the model ~10–30 s of output at 15 tok/s |
| Results per search (`limit`) | **5** (max 8) | The main model judges 5 rows nearly for free |
| Discovery receipt size in context | **≤ ~1.5k tokens per call, ≤ 3k total** | About 2% of 128k, so it doesn't push compaction |
| Wall clock per `discovery_search` | **soft cap 45 s** (`maxDiscoveryMs`) → `budget_exhausted` receipt | browser39 can take 5–30 s |
| Categorizer (if on) | **≤ 5 s added, 0 extra steps** | Runs *inside* the search call |

## 3. Architecture pick: **A now, B as an optional in-tool stage, never C**

`discovery_search` returns a **compact, triaged table**: real URLs, title, host, and deterministic flags (`dup_host`, `login_cue`, `token_miss`, `denylisted`), already sorted. The **main model** picks 1–2 rows and calls `mission_fetch`. Fetch is the preview: missions already returns `thin` / `js_shell` / 404 and records a ledger row. If the result is bad, the model moves to the next row from the same table without searching again.

**Changed from P0.5:** `discovery_preview` and `discovery_scan` are **cut from v0**. Preview would duplicate `mission_fetch` (same browser, same cost, but no ledger). Scan duplicates missions' depth fence. Both can return later only if the kill criteria below show they're needed.

## 4. The categorizer (B): an interface, optional, inside the tool

- **When:** inside `discovery_search`, after the engine responds and the heuristics run, before the receipt is returned. **0 extra agent steps.**
- **Input:** goal/query plus ≤ 8 rows of `{url, host, title, snippet?}`. **Output:** labels only, per row: `{i, label: "primary"|"reference"|"forum"|"commercial"|"junk", keep: bool}`. **It never rewrites the query and never fetches.** That rule is what keeps it from turning into a nested researcher.
- **Transport:** one **OpenAI-compatible `/v1/chat/completions` client** with config `{ categorizerEndpoint, categorizerModel, categorizerApiKeyEnv, timeoutMs }`. That one interface covers:
  - local llama.cpp / ollama on its **own port** (never `:8080`);
  - OpenRouter or any hosted model (**opt-in, breaks ISO / local-first**: README and the receipt must say `categorizer: remote`).
- **VRAM reality:** a 27B Q4 model with a 128k KV cache already fills 32 GB. A 1–2B model (Qwen2.5-1.5B / similar, Q4 ≈ 1–1.5 GB) is **recommended on CPU**: classifying 8 rows of titles is a few hundred tokens and takes a few seconds on CPU. It needs no GPU, so there's no fight for VRAM.
- **Failure:** endpoint empty → off. Timeout, error, or bad JSON → receipt says `categorizer: "unavailable"` and falls back to heuristic order. It never fails the search.
- **Determinism:** temperature 0, JSON schema, and the label set is closed. Hermetic smoke uses a stub HTTP server, like SearXNG today.

## 5. How the main model picks (skill + receipt)

Receipt sketch (this is the size budget):

```
{ ok, query, engine, count, categorizer: "off"|"local"|"remote"|"unavailable",
  urls: [ { i, url, host, title, snippet?, flags: [...], label? } ]   // sorted, ≤5
}
```

Skill copy (missions `web-mission-workflow`):

- With `discovery_search` present, **never invent or recall URLs**. Start with one search and use the query from the mission Goal.
- Fetch the top 1–2 rows that aren't flagged. On `thin` / 404, take the next row; **don't search again unless every row failed.**
- `no_engine` → tell the user and ask for URLs. **Don't fall back to memory.**

## 6. Engine order

**Operator lock:** browser39 is #1 (we know and trust the author; make it as good as possible). The auto order becomes `browser39 → searxng → yacy`. Because the others are only fallbacks, `browser39_blocked` (DDG captcha, HTTP 202) **falls through quickly**.

Making browser39 good (P_02):

- Find out what the CLI actually offers: backend selection (non-DDG?), result count, any snippet or `markdown` content in the reply we currently ignore, and speed flags. If the SERP markdown contains snippet text, map it in. Titles alone are weak input for triage.
- Talk to the upstream author about a structured `search --output json` that returns `{url,title,snippet}` results. That's cleaner than our `uddg` unwrap and would be a good upstream contribution.

**SearXNG / YaCy as our dependencies:** no CORS concern. The Node host makes the HTTP call server-to-server, so no browser is involved.

- **SearXNG:** a Python app. The simplest setup is one Docker container (~200 MB) on `:8888`. **Gotcha:** `settings.yml` must enable `search.formats: [html, json]`, or the JSON API returns 403. Provide a documented `docker run` / compose snippet; don't vendor it.
- **YaCy:** Java, heavy (~0.5–1 GB RAM), and its own index is **empty** unless you crawl or join the P2P network. Its search quality is low for our use. **Ship the adapter plus a stub test to prove the N-engine registry; don't install it.**

## 7. Non-goals

- No DIY DDG/HTML scrape (Eris scar).
- No subagent, background worker, or parallel fan-out.
- No `discovery_preview` / `discovery_scan` in v0.
- The categorizer never fetches, never rewrites queries, and never loops.
- No cloud categorizer **by default** (opt-in only, labelled `remote`).
- No sidebar UI.
- No vendored SearXNG/YaCy install scripts beyond a README snippet.

## 9. Kill criteria (check after ~20 dogfood missions)

- **Core metric (two binary checks per mission; the baseline is too noisy to compare against: 6/6, 4/8, 2/6 good fetches across a few runs):**
  1. **Used:** the agent called `discovery_search` and fetched from its rows, with no invented or recalled URLs.
  2. **Exists:** the fetched URLs resolve (no 404 / DNS fail).

  Target: both checks pass in **≥ 90%** of missions where discovery is on. If not, fix the skill or the engine before adding features.
- **Useful (added after critique):** at least one mission note came from a discovery URL in **≥ 70%** of missions. "Exists" alone can be a real but useless page.
- **Contract readiness (gate for replacing DSH web search):** both checks above stay green across ~20 missions on both engines, with no contract changes needed.
- **LLM categorizer:** turn it on for half the runs. If "good first fetch" improves by less than ~15%, or it adds more than 5 s on average, **remove it**.
- **browser39 #1:** if it's blocked in more than ~30% of searches or the median is above 20 s, demote it behind SearXNG (revisit the lock).
- **Preview/scan revival:** only if the logs show the model regularly burns 3 or more fetches to find a keeper.
- **Discovery tokens:** if the receipt pushes compaction earlier in real runs, cut `limit` to 3.

# P_05 — Discovery as a sub-step of missions

**Shape decision:** missions **depends on** `dsh-web-discovery` (bundled npm dependency), and the code stays in its own repo. Merging the codebases later is still possible and costs nothing extra if the port stays clean.

## Steps

1. Missions adds the dependency and calls the core through `DiscoveryPort` directly. The `discovery.json` file bridge stays as the record, not as the transport.
2. **Flow:** on `mission_start`, when discovery is active, missions runs the search from the Goal (or tells the agent to do so first). User URLs are added as seeds.
3. **Engine select** in the missions UI/config: `auto | browser39 | searxng` (later a hosted backend). It's stored per mission or profile.
4. Health/badge shows the engine actually used and the categorizer mode.
5. **README:**
   - the SearXNG docker snippet, with the `formats: [html, json]` gotcha;
   - an honest note that search queries leave the box through upstream engines.
6. **Cycle check:** discovery must never import missions (one-way dependency).

## Acceptance

- One install gives both packages; discovery works with no separate profile wiring; the engine select works; tests green in both repos.

## Open
